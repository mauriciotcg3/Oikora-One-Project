## 2. Contrato e comportamento

Consumir exclusivamente o contrato aprovado por `shared/http`. O backend decide todas as capacidades; o frontend usa `/me` apenas para navegação e conforto. Mostrar duração máxima de 72 horas, escopo, justificativa e categorias sensíveis explícitas. Não oferecer governança ou exportação. O aprovador não edita o pedido: aprova integralmente ou recusa com justificativa. Tratar 403, 409 e 422 de forma visível; em 409, recarregar e não repetir a mutation automaticamente.

## 3. TDD e gates

Começar pelos dois testes RTL da T-48; obter aprovação, confirmar Red e só então implementar. Cobrir os seis casos da task. Rodar teste focado, tipos estritos, lint arquitetural e gate frontend pelos comandos registrados em `docs/agents/project.md`.

## 4. Fronteiras

Fluxo `shared → features → pages → app`; componentes de UI recebem dados/callbacks e não chamam HTTP. Estado remoto fica no mecanismo de server state; formulário/modal permanece local. Exportar apenas a Public API da feature. Nenhuma dependência de Fuse, nome de papel, posição de menu ou `localStorage`.

## 5. Restrições da sessão

Uma task por sessão; branch `t-48-ui-solicitacoes-permissao` a partir da integração definida pelo projeto. Não alterar ADR, backend ou outras features. Sem commit, push ou publicação automática. Decisão arquitetural nova exige pausa e `architectural-decision`.
